# Card Vault

简体中文 | [English](./README.en.md)

Card Vault 是一个本地优先的球星卡收藏管理工具，用于录入、筛选、展示和桌面端运行个人收藏数据。

项目使用 `Next.js + React + Prisma + SQLite + Electron` 搭建。卡片数据和图片默认保存在本地，适合离线使用，也支持在桌面端切换数据存储路径。

## 当前版本

- `1.0.10`

## 版本说明

### 1.0.0 基础版本功能

`1.0.0` 是项目的首个完整可用版本，具备本地收藏管理和桌面端运行所需的核心能力。

- 支持新增、编辑、删除球星卡。
- 支持上传卡片图片并进行本地保存。
- 支持首页按关键词、运动类型、球队、年份、产品线、签名卡、评级状态等条件筛选。
- 支持按录入时间、年份、价格、评级排序。
- 支持卡片详情页查看图片、基础信息、购买信息、评级信息和备注。
- 支持“展示”浏览全部卡片，并进入单卡展示详情。
- 支持 Electron 桌面端运行。
- 支持本地 SQLite 数据库存储。
- 支持本地图片目录与数据库分离保存。
- 支持在设置页切换桌面端数据存储路径。
- 支持生成 Windows 安装版和便携版发布包。

### 1.0.8 升级内容

`1.0.8` 是一次稳定性与可维护性阶段升级，包含用户行为修正、数据安全加固、桌面端启动保护、资源生命周期管理、性能清理和核心模块拆分。以下改动统一归入本版本。

#### 功能与行为修正

- 首页“总估值”仅统计“持有中 / 在售 / 送评中”卡片，“已售出 / 目标卡”不再计入持有价值。
- 卡片排序移除“评级升序”和“评级降序”。

#### 数据与资源安全

- 更换存储路径时会完整迁移卡片图片、分享封面和分享背景。
- 一键备份改为生成 SQLite 一致性快照，并在完成后自动执行数据库完整性检查。
- 卡片图片、分享封面和分享背景统一增加 15MB 大小限制、真实文件格式校验和安全扩展名。
- 上传或数据库保存失败时自动清理未使用文件；替换或删除分享集时同步清理旧封面和旧背景。

#### 桌面端可靠性

- Electron 增加单实例保护，避免重复启动多个 Card Vault 进程。
- 本地服务增加 Card Vault 身份健康检查，防止误连接到同端口的其他服务。
- 默认端口被占用时自动选择可用端口，并将实际地址交给桌面窗口使用。

#### 代码清理与性能优化

- 清理未使用的旧卡片创建入口，新建与编辑卡片共用同一套表单字段转换逻辑。
- 卡片图片、分享封面和分享背景路由共用统一的图片响应工具。
- 首页、展示和分享选卡页面只读取实际需要的首张图片，减少无效数据库读取。
- Azure OpenAI 与 MiniMax 共用统一的 AI 请求客户端，集中处理超时、错误信息和模型参数兼容回退。
- AI 设置模块改为服务商无关命名，降低后续增加模型服务商时的维护成本。
- 分享导出拆分为流程编排、公开数据映射、页面渲染、类型定义和 ZIP 归档模块，避免单文件持续膨胀。

#### 质量保障与维护工具

- TypeScript 启用未使用变量和参数检查，避免无效代码再次积累。
- 新增关键自动化测试，覆盖首页价值规则、AI JSON 解析与模型参数回退、图片真实性校验、存储迁移、数据库备份、分享隐私字段白名单和 ZIP 目录结构。
- 新增 `npm test` 与 `npm run check:release`；发布检查会依次执行 UTF-8 编码检查、TypeScript 类型检查、自动化测试和 Next.js 正式构建。
- `1.0.8` 不新增数据库业务字段，现有 `1.0.7` 数据可直接继续使用；升级前仍建议执行一次完整备份。

- 桌面端和移动端使用独立响应式结构，手机端保留触控切换并避免标题、展区和卡片溢出。

#### 章节化内容编辑

- 分享集新增可排序的展馆章节，可为每个章节设置标题、正文和“图文叙事 / 横向展带 / 卡片矩阵”布局。
- 卡片可分配到指定章节，每张卡片最多归属一个章节；未分组卡片仍保留在主展区中。
- AI 生成的收藏叙事、主题亮点和分组说明会转换为可继续编辑的章节草稿。
- 新建和编辑分享集时提供实时展馆预览，布局、主题、背景焦点和章节修改可即时查看。

#### 一致性与维护

- 应用内预览、静态导出包和云端发布包改为共用同一套 HTML、CSS 和交互渲染器，减少预览与导出效果不一致。
- 新增版本化的展馆展示配置和章节数据模型，并兼容尚未设置章节的旧分享集。
- 删除旧的 React 分享预览组件，集中维护轮播、主题和响应式行为。
- Windows 打包排除约 100 MB 的 Next.js 构建缓存，减少安装版与便携版体积，不影响运行时文件。
- 扩展自动化测试，覆盖展示配置解析、主题变量、章节保存、三套布局以及统一预览渲染。
- `1.0.10` 会自动补充本地数据库结构；升级前建议先在设置页执行一次完整备份。

## AI 识图录入

顶部“设置”页提供全局 AI 设置；新增卡片和编辑卡片页面提供 AI 识图录入 / 填充入口。当前支持 Azure OpenAI 和 MiniMax。

- 桌面端会把 AI 设置保存到本机用户数据目录中的 `ai-config.json`，不会写入 Git 仓库或卡片数据库。
- Azure OpenAI 设置项包括 Endpoint、API Key、Deployment 和 API Version。
- MiniMax 设置项包括 API Endpoint、API Key 和 Model。
- 开发态可以通过 `.env.local` 配置 `CARD_VAULT_AI_PROVIDER`，并按服务商填写 `AZURE_OPENAI_*` 或 `MINIMAX_*`。
- 识图录入支持 1-2 张 `jpg/png/webp` 图片，适合上传卡片正面和背面。
- 已录入卡片可在编辑页使用已有默认图片进行 AI 填充。
- AI 结果只作为录入建议填入表单，用户可以继续修改后再保存。
- 默认只填空字段，勾选“覆盖当前字段”后才会替换已有输入。

## 分享与云端发布

顶部“分享”用于创建面向他人的分享集。分享集独立于本地“展示”，默认由用户手动挑选卡片。

- 分享集支持标题、副标题、封面介绍、展馆叙事、收藏亮点、主题分组、封面图和自定义背景图。
- 分享集支持选择通用主题、运动主题或球队主题；当前包含“聚光灯展馆”“经典档案馆”、足球、篮球、网球、F1 和“蓝黑军团-1 / 蓝黑军团-2”，主题会同步应用到本地预览、静态分享包和云端发布包。
- 分享集可调用当前全局 AI 设置生成中文展馆文案，AI 结果只填入草稿，用户可继续修改。
- 分享集封面支持自动使用第一张有图卡片，也支持自定义上传；自定义封面保存在独立的 `share-covers` 目录，便于和卡片图片分开管理。
- 分享集背景图支持自定义上传、保留和清除；自定义背景保存在独立的 `share-backgrounds` 目录。
- 分享集支持为单张卡设置展示标题、展示描述和排序覆盖，不影响原始卡片数据。
- 分享集预览和导出的静态展馆支持纯图片 3D 卡片切换，桌面端可点击切换，手机端可滑动切换。

- 云端发布包会额外生成 `README-deploy-cloud.md` 和 `nginx-card-vault-share.conf` 示例配置，适合上传到服务器静态目录。

## GitHub 仓库与本地运行说明

以下目录或文件通常不建议提交到 GitHub：

- `.env`
- `node_modules`
- `.next`
- `dist`
- `data`
- 本地数据库文件

原因是它们属于本地配置、依赖安装结果、构建产物或个人数据，不适合作为源码仓库的一部分。

但要注意：这些文件虽然通常不提交到 GitHub，对“当前这份本地可直接运行的工作目录”来说，其中一部分是运行必需项。例如 `node_modules` 和 `.next` 如果被删除，本地桌面端就无法直接启动，必须重新安装依赖并重新构建。

因此建议区分两种使用方式：

- GitHub 仓库用于保存源码、文档和配置。
- 安装版 / 便携版用于给第三方电脑直接运行。

## 项目体积与阶段维护

当前开发目录体积主要来自 `node_modules`，这是 Electron、Next.js、Prisma、TypeScript 等依赖安装后的实际文件，不属于源码本身。`node_modules` 通常不提交到 GitHub，但保留它可以让本机继续直接开发运行。

阶段性清理原则：

- 可安全清理：`.next/cache`、`logs`、`tsconfig.tsbuildinfo`、旧的 `dist` 构建产物。
- 谨慎清理：完整 `.next` 会影响生产启动，需要重新 `npm run build`。
- 不建议随手清理：`node_modules`，删除后必须重新执行 `npm install`。
- 不要清理或提交：本地数据库、上传图片、AI Key、`.env` / `.env.local`。

推荐阶段检查流程：

```bash
npm run clean:cache
npm run check:release
```

分享功能已经合并到 `master`。开发新功能时建议使用独立分支，完成 `npm run check:release` 和桌面端关键流程回归后再合并。

## 跨电脑同步与编码约定

项目源码统一使用 `UTF-8` 编码，并通过 `.editorconfig` 和 `.gitattributes` 固定常见文本文件的编码与换行规则。

在不同电脑之间通过 GitHub 同步源码时，建议：

- 使用支持 `.editorconfig` 的编辑器，并确认文件以 `UTF-8` 打开和保存。
- 不要用 GBK、ANSI 或系统默认编码重新保存 `.ts`、`.tsx`、`.js`、`.md` 等源码文件。
- 提交前运行 `npm run check:encoding`，检查源码是否出现典型中文乱码或非法 UTF-8 内容。
- 收藏数据仍然按“数据备份说明”单独迁移，不要提交本地数据库、图片、构建产物或日志。
