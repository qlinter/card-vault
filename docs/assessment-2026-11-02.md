# Card Vault 开发状态评估与下一阶段准备

评估日期：2026-11-02。源码基线：`02339cf`，`package.json` 版本 `1.5.0`。本次开始时 Git 工作区干净。运行环境：Windows、Node.js 24.14.0、npm 11.9.0。

这是当前代码的评估快照和待办建议，不替代现行规范，不表示下一版本功能范围已经确认。所有业务验证使用隔离收藏库；未修改实际收藏、配置、备份或业务源码，未发布、打包或推送。

## 结论

项目处于“核心功能完整、已有工程化交付能力、适合继续个人使用和受控迭代”的阶段。下一阶段可以启动，但应先修复已复现的重复提交和旧表单覆盖问题，并恢复可重复通过的质量基线。

收藏录入、财务核算、展示分享、导入导出、备份恢复已构成完整闭环；没有证据支持现在重写技术架构或再次整体改版。当前最值得投入的是保存可靠性、测试可复现性，以及真实使用反馈驱动的小步改进。面向更多用户分发时，再提高迁移、误操作恢复和干净机器验收的要求。

不使用“整体完成百分比”：下一阶段需求尚未确定，功能存在、测试通过和发布可用是三个不同维度。

## 架构与可维护性

`app` 承担路由和操作入口，`components` 负责交互，`lib` 负责领域规则与服务，`electron` 管理桌面和存储，`scripts` 负责数据库结构、验证与发布。运行时同时存在 Prisma 和 Node SQLite，前者处理应用查询，后者承担结构校验、快照和测试等职责。

本次架构检查覆盖 383 个源文件，未发现依赖循环，153 个客户端可达模块没有越过 Node.js/数据库边界。Git 跟踪的 app/components/lib/electron/scripts 中代码与 CSS 约 3.5 万行，tests 约 1 万行；计数只用于理解规模，不作为质量评分。

值得保留的设计：

- 财务金额使用整数最小货币单位，缺失金额与零分开，持仓/收益由共用逻辑计算。
- 数据页采用 250 张卡片一批的聚合、数据修订号和时间有效期缓存；缓存有条数和大小上限。
- 导入逐行事务、状态记录及撤销前指纹检查，比一次性全量写入更容易恢复。
- 备份恢复暂停本地服务，使用清单、暂存目录、回滚目录和恢复日志，已有中断边界测试。
- 分享导出明确列举公开字段；Electron 使用 contextIsolation、sandbox、关闭 nodeIntegration，并检查 IPC 来源。
- CI 已覆盖依赖审计、类型、Lint、架构、单元、HTTP、UI 与构建；发布脚本另有包内验收和产物校验。

维护成本主要集中在三个方面：

1. Prisma 模型、手写 SQLite 建表/触发器、恢复校验及格式兼容需要共同维护。增加字段时，应逐项定义新库、旧库升级、备份恢复、导入导出与失败回滚，而不是只修改 Prisma。
2. `PortfolioSavedView`、`PortfolioSnapshotRecord`、旧 Scout 关系表仍承担兼容职责。保留不等于忘记删除；下一阶段不能按“界面不用了”直接删表。
3. 少数复杂组件仍偏大，例如 `create-card-form.tsx` 和 `ai-settings.tsx` 约 400 行。只有实际修改涉及这些职责时再拆分；当前没有必要发起全项目结构重写。

## 已确认问题与风险

### F1 · P1：新增卡片重复提交会重复入库（已复现）

位置：[录入服务](../lib/card-entry-service.ts)、[新增操作](../app/actions/cards.ts)。

复现：在隔离库建立一份普通录入草稿，读取 `/cards/new` 的 Server Action 字段，携带同一个 `draftId`、同一图片和字段，对普通新增路径连续发送两次相同 POST。两次均返回 303 和不同的卡片 ID；数据库产生 2 张卡片，草稿为 0 条。

服务端会验证批量队列项目是否已被处理，但普通新增没有等效的提交标识。删除草稿没有阻止相同草稿请求重放。前端提交按钮禁用、重复候选提示也不能保证请求只生效一次。

影响：提交响应丢失后重试，或者同一草稿在两个页面提交，可能重复建立档案及随档案创建的初始财务。后者为代码路径推断，本次复现只创建档案和图片。

建议：给一次用户提交分配稳定标识，在数据库事务内保证唯一；重复请求返回首次创建结果。不能按主体/卡名永久去重，因为收藏者可以合法持有同款多张。

验收：同一标识顺序/并发重复提交都只产生一份档案、图片关系和初始财务；首次成功但响应丢失后重试返回原 ID；主动新增另一张相同卡片仍然允许。

### F2 · P1：旧编辑表单可静默覆盖新内容（已复现）

位置：[档案更新](../app/actions/cards.ts)、[编辑表单](../components/edit-card-form.tsx)。

复现：从同一次读取构造 A、B 两份编辑表单。A 将卡名由 `Original` 改成新名称并保存；B 保留旧卡名，只修改备注后保存。两次都返回成功，最终卡名退回 `Original`，备注为 B 的新备注。

当前更新只按 `id` 写整份档案，没有对读取时版本进行条件更新；事务保护写入一致性，但不能识别表单是否过期。

建议：在表单中携带读取版本，服务端使用条件更新；冲突时保留输入并显示差异，不自动覆盖。财务编辑和分享编辑也应按同一原则检查，不能直接把档案的复现结论推广为其全部路径均已验证。

验收：两份旧表单修改不同/相同字段、财务改变收藏状态后再保存旧档案，都不会无提示丢失已保存信息。

### F3 · P1：当前质量基线不能直接宣称全绿

- 原始 `test:coverage` 结果为 349/352，通过率之外的 3 项都是启动器夹具失败。
- 环境存在 `NoDefaultCurrentDirectoryInExePath=1`，测试使用 `cmd.exe /d /c start-desktop.bat`，依赖隐式查找当前目录。诊断中只把测试调用改为显式 `.\start-desktop.bat`，保持环境保护不变，3/3 通过。业务启动器源码未修改。
- 现有 2026-10-28 日志记录完整 UI 157/158，并且心愿测试独立复跑两次均因 `getByRole("alert")` 同时匹配业务错误与 Next.js route announcer 而失败。位置：[心愿测试](../tests/ui/scout.spec.mjs)。这是已知测试定位问题，不能据此断言心愿预算校验失效。
- 本次默认浏览器路径缺少 Playwright 需要的 headless shell，最初的界面/展示检查未能启动浏览器；这些结果属于环境失败，不是 158 个产品缺陷。后续验证记录见下文。
- 补齐指定浏览器后，本次完整 UI 为 **157/158 通过**，耗时约 7.5 分钟；心愿场景及全部截图比较通过，没有更新截图或放宽阈值。唯一失败为 `financial.spec.mjs:131` 的历史多币种交易纠错场景，随后独立连续复跑 **3/3 通过**，因此标记为间歇性问题，不能直接把完整回归记为通过。

财务失败轨迹中，第一次提交 USD 被正确拒绝，测试随后选择 CNY 并填写备注，但第二次实际 HTTP 请求的币种仍为 USD，服务端再次拒绝，数据库备注未更新。页面快照也显示币种回到了 USD。需要重点排查 [PersistentForm](../components/persistent-form.tsx) 的失败值恢复、下一帧回填与新输入之间的竞争，以及用例交互时序；尚未确定唯一根因。这比单纯调大等待超时更值得检查。

建议：固定浏览器准备方式；启动夹具用显式路径；错误定位限定到业务工作区及具体提示；修正财务失败恢复与重试的时序问题；新增 F1/F2 的行为回归。不要放宽截图阈值或仅靠重复运行掩盖问题。

### F4 · P2：依赖审计已出现新的中等级公告

2026-11-02 联网结果：全部依赖 31 个中等级受影响节点，生产依赖 8 个；两者高危与严重级别均为 0。节点来自同一条 `minimatch` 公告，不是 31 个彼此独立的漏洞。生产路径涉及 `archiver`、`exceljs` 及其传递依赖。

公告描述特定 glob 模式预处理可能放大 CPU/内存消耗，修复版本列为 11.0.1；公告晚于 v1.5.0 的发布验收。[上游安全公告](https://github.com/advisories/GHSA-g3hv-75wg-m249)

当前审计命令使用 `--audit-level=high`，所以退出码仍为 0，不能解读为没有告警。本次没有证明应用界面允许攻击者传入相应 glob 模式，也没有复现漏洞利用。

建议按实际调用链评估暴露面，再选择兼容依赖修复并回归 ZIP/XLSX 和打包。审计自动修复建议包含主版本变化甚至降级，不应直接执行 `audit fix --force` 或全链强制覆盖。

### F5 · P2：数据恢复能力与日常纠错能力存在边界

卡片删除直接删除档案并清理图片，关联财务使用级联删除；财务更正覆盖原记录并标记 `manual_correction`，未保存完整前后版本。当前没有通用回收站或逐笔历史回退。已有导入撤销、提醒撤销、分享编辑历史和完整备份不应被误认为能覆盖这些情况。

这在既有版本中是明确未纳入的能力，不是本次发现的已承诺功能缺失。若下一阶段选择长期资料可靠性，建议先确定卡片删除恢复和财务更正留痕的范围、保留期限、图片引用及冲突规则，再设计增量数据模型；保留当前手动备份选择，不擅自恢复已取消的自动备份。

### F6 · P2：下一次迁移需明确区分兼容升级与历史清理

`ensureScoutReady` / `ensurePortfolioReady` 可在页面读取时触发按 `PRAGMA user_version` 控制的一次性历史清理，旧库恢复后也可能再次进入该路径。清理范围、先行安全副本和授权来源已在 v1.5.0 文档记载；本次没有运行这些操作到实际收藏库，也不重新质疑既有授权。

下一阶段若增加状态历史、审计或回收站，应建立显式升级清单，分别描述结构变化、业务记录变化及恢复后行为。不能把历史版本的定向清理授权延伸到新功能或新数据。

交付门槛：原始单元命令、构建、HTTP、UI 正常比较可通过；重复请求与旧表单测试稳定；未丢失旧收藏、图片及财务；不以放宽规则换取通过。

### 阶段 B：按实际使用反馈选一个产品主题

建议主题为“可靠地长期管理收藏”，优先评估删除恢复、财务更正留痕、状态变更历史；每项先定模型与兼容，再决定是否实现。它们是候选方向，不自动计入已授权开发范围。

如果实际最大痛点是录入耗时，则改以录入效率为主题：先用一批有代表性的卡片测量人工录入时间、AI 候选纠正量、草稿恢复成功率和模板复用效果，再选择具体优化。不要同时启动可靠性、行情采集、云同步和整体视觉改版四条产品线。

交付门槛：选择的主题有具体使用场景、可观察的改善和明确兼容测试；维持现有三项主导航及渐进展开的方向，除非真实反馈要求改变。

### 阶段 C：按分发目标决定发布范围

- 若继续个人使用：阶段 A 完成后即可逐步进入功能开发，保留手动备份与版本回退资料。
- 若准备给更多收藏者使用：补充旧库升级/恢复矩阵、干净 Windows 安装与卸载、包内端到端回归、版本及校验清单核对；代码签名按分发目标决定。
- 发布 CI 当前上传安装包、便携 ZIP 和 SHA256SUMS，但未列入 `release-*.json` 构建清单，建议与本地发布契约对齐。
- 长期在线发布、多设备同步、独立手机应用及自动行情暂不纳入本轮默认计划，它们需要重新确定账户、托管、成本和数据冲突方案。

不在本次提前确定下一个版本号或工期；先完成阶段 A，依据选定的产品主题和数据兼容范围制定里程碑。

## 评估后的修复（2026-11-02）

用户在评估后授权修复重复入库、旧表单覆盖及测试不稳定。本节记录后续未发布源码，前面的评估结果保留为修复前基线。

- F1：新增录入使用稳定的提交身份。普通表单在动作状态中保存提交标识；草稿和队列使用各自身份，重试及同一草稿的多个页面返回首次保存的卡片。现有卡片主键负责数据库级唯一性，先占用主键再消费草稿/队列和写入图片、初始财务；并发落败请求清理自己暂存的图片。新开空白录入仍能保存同款独立卡片。提交前草稿同步失败时保留输入并停止本次提交，避免重试时改变身份。
- F2：编辑页保存读取时的档案/图片指纹，在图片上传前和数据库事务内检查，拒绝旧表单覆盖。冲突后保留输入及已选图片，重复点击也不能绕过保护；重新打开编辑页核对最新资料后可以保存。指纹不依赖毫秒时间戳；仅财务时间和数量改变不误报冲突，同页财务引起的状态变化按既有流程同步，其他档案或图片变化不能自动重置旧表单的保护基线。
- F3：财务表单阻止自动重置，成功由页面跳转或父组件重建表单；移除失败后下一帧回填旧值的逻辑。历史交易场景现在主动延迟浏览器帧，在纠正币种后释放帧，验证旧输入不能覆盖新选择。心愿断言限定到业务区域及具体金额提示，启动器夹具改用显式路径，并始终启用禁止隐式当前目录查找的环境设置。
- 原生表单补充修复：编辑操作在服务端页面绑定卡片身份后传给表单，避免原生错误返回时在渲染重试中不断创建新的绑定 Promise。HTTP 回归覆盖原生校验失败、纠正重试、旧表单与并发编辑，不仅依赖已接管页面的浏览器调用。
- 没有修改数据库表、字段、初始化、迁移、备份或导出格式；本次没有对实际收藏库执行数据操作。版本号仍为 1.5.0，未生成新安装包、便携包或发布。

验证记录：354 项单元与模块测试及覆盖率门槛通过，行 94.29%、分支 86.97%、函数 91.81%。完整界面回归 160/160 通过，包含新增中英文冲突场景和全部原截图比较，未更新基线或放宽阈值。其后针对原生操作引用和草稿准备边界补充修整，并增加一项草稿失败重试检查；最终相关界面回归另行记录在 `logs/write-safety-final-ui.log`。新增 HTTP 检查随 `npm run test:card` 执行，覆盖顺序/并发重试、同一草稿跨页面、队列消费后重试、合法同款卡、验证回滚、并发档案修改、图片/状态冲突和暂存文件清理。
