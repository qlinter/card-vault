# Card Vault 产品开发路线图

最后确认：2026-09-05。

本文档记录 Card Vault 的长期产品方向，供需求取舍、阶段规划和发布验收参考。路线图按能力阶段组织，不预先锁定具体版本号；实际发布版本可根据工作量、数据风险和完成情况决定，但应保留本文确定的产品原则和阶段顺序。

## 产品定位

Card Vault 将继续以“本地优先的个人球星卡收藏管理工具”为核心，逐步从收藏档案工具发展为个人收藏资产管理与展示平台。

后续建设围绕四条主线展开：

1. 更快录入和维护收藏数据。
2. 建立可解释、可追溯的持仓与收益体系。
3. 提供由确定性数据支撑的组合分析和收藏决策辅助。
4. 提升分享展馆的成品质量，并在资源成熟后提供可选的在线发布与同步。

## 开发原则

- 优先改善高频操作，再扩展低频高级能力。
- 本地功能不依赖在线账户或持续联网。
- 用户数据、图片和财务历史默认保存在本机。
- 程序负责金额、比例、收益和趋势等确定性计算；AI 负责识别、解释、归纳和建议。
- CNY 与 USD 保留原币事实；统一报表只使用设置中用户确认的人工汇率。
- 高风险数据迁移与大型界面改版不放在同一个开发批次或正式发布中。
- Cloudflare Drop 继续作为人工临时发布渠道，直到具备长期服务器或正式 Cloudflare 项目资源。
- 功能增长不得削弱现有备份、恢复、本地会话安全、测试覆盖率和可重复发布基线。

## 已确认财务方案：统一开发批次

状态：下列统一批次已完成并通过整体验证；下文保留已确认的开发和验收要求。语言菜单与导航已完成源码和针对性验证，不重复安排。用户自行替换当前启动所用的旧数据库，不新增该旧库的升级路径；后续财务结构变更以届时实际使用的数据库基线为准，不能据此清空或覆盖现有收藏。

先修复备份一致性，再以一个统一财务批次完成数据结构、核算引擎、设置中的人工汇率、录入、全部财务页面和发布验收。下面六项是同一批次内部的实施依赖，不是六个交付批次；不分阶段启用、不拆成多个财务版本、不在每项结束后重新等待启动指令。必要测试随实现完成，最后统一验收交付；任何一项未完成，整个财务批次都保持未完成状态。

### 前置批次：备份一致性与开发基线

- 备份时统一限制并排空写入，覆盖卡片、财务、分享和图片队列，保证数据库与媒体来自一致状态。
- 验证备份中的媒体引用；备份失败须恢复正常写入并给出可操作错误。
- 用隔离测试库复现并验证新增、换图、删除与队列处理期间备份，再演练恢复。
- 开发开始时确认实际使用的数据路径与数据库结构，只读取元数据进行确认；保留完整安全备份。
- 验收：不再出现缺图却报告完整成功的备份；恢复后卡片、财务和媒体关联一致。

### 内部工作 1：明确业务规则与验收样例

- 定义一次交易的数量与多个付款/收款组成，区分一张卡混合付款和分别买入多张同款卡。
- 明确估值展示币种、报价选择、汇率适用日期、成本分配精度、同日交易排序、后补费用、记录纠错及已售状态规则。
- 首期采用手动录入并确认汇率，统一在“设置 → 财务设置 → 汇率管理”维护，保存币种对、方向、日期和来源；自动获取汇率留到后续。
- 建议默认报表币种 CNY，允许选择 USD；优先使用所选币种的最新直接报价，缺少直接报价时只有具备明确的估值换汇依据才能折算，否则显示未估值。该默认值属于本批次实施设计，不视为已经上线。
- 汇总展示估值覆盖和可计算收益覆盖；缺少任一必要成本、收入或换汇依据时，完整收益为空并列出缺项，不能用 0 冒充。
- 验收：人民币买入/美元费用、跨币种出售、混合付款、同款多张、部分出售、不同日期双报价、缺少汇率、无交易历史均有明确预期结果。

### 内部工作 2：建立数量与金额分离的数据结构

- 交易主体保存卡片、买入/出售类型、一次数量变化和业务日期；关联付款/收款明细保存原币种及最小货币单位金额。
- 费用关联对应持仓或交易；估值独立保存币种、日期、来源；换汇依据可追溯到具体计算用途。
- 记录未知成本与已知零成本的区别；不能将历史金额为零的记录全部推定为免费取得。
- 以当前实际基线设计备份、事务变更、回滚和版本标记；既有交易默认保持原意，含糊的多币种记录进入核对清单，不自动合并数量。
- 验收：一笔多币种买入只增加一次数量，原始金额与媒体关联完整保留，重复执行不重复记账；未知或不支持结构应明确拒绝。

### 内部工作 3：实现统一持仓与原币种成本计算

- 统一数量增减及超卖校验，出售收款币种不限制实物可售数量。
- 买入和评级费用按原币种组成计入库存成本；移动平均法分别结转每种币种成本，最后售出吸收尾差。
- 出售费用进入净收入，完整保留原币种现金流；新增、修改、删除记录后按业务时间重算。
- 验收：不重复计算数量，不遗漏外币费用；每个币种的剩余成本与结转成本守恒，跨币种出售与部分出售结果正确。

### 内部工作 4：实现设置中的汇率管理、双报价与收益计算

- “设置”提供财务设置区域：报表币种选择、人工汇率新增/维护、日期及来源、历史记录。汇率方向明确展示为“1 USD = … CNY”，避免把双向汇率当作两份独立数据输入。
- 财务业务页面不再设置独立的人工汇率输入框；只展示所用汇率、日期、来源和缺失原因，缺少汇率时提供前往设置的入口。
- 汇率记录进入本地数据库及备份恢复范围，不能只存在浏览器偏好设置中；新增记录不覆盖已保存的历史依据，修正汇率须保留可追溯版本和受影响计算范围，历史快照保持原样。

- 同一数量对应两种报价，分别保留，不把两种报价作为两份资产相加。
- 历史成本按对应事实的确认汇率折算，出售收入按出售事实的确认汇率折算，估值按明确的报价/估值日期口径计算；不能用今天的汇率改写历史成本。
- 首期保留原币种账本，不单独拆分投资收益和汇兑损益；使用何种汇率以及缺少什么依据必须可查看。
- 输出明确的完整/不完整状态；所有数据齐全后才输出完整已实现、未实现收益和收益率。快照保存算法版本、报价与换汇依据，后续更新不静默重写历史快照。
- 验收样例：1 张卡买入 CNY 1,000、评级 USD 20；评级费用确认汇率为 1 USD = 7 CNY，选用 CNY 1,500 估值，则成本为 CNY 1,140、未实现盈亏 CNY 360；删去必要汇率后完整收益不可计算。以上仅为固定测试值。

### 内部工作 5：统一录入与全部财务页面

- 录入支持一次交易、多种付款/收款组成；费用归属和报价币种有清晰入口；所用汇率来自设置中的对应日期记录，缺失时指引至设置补充，不在交易表单重复输入汇率。
- 详情展示统一数量、原币种成本组成、不同币种报价及收益缺项；页面新增文案使用明确翻译键，并保护用户内容不被整页翻译修改。
- 首页、组合当前数据、结构分析、历史趋势、比较、排序、保存快照和 AI 分析摘要全部读取统一财务输出。
- 历史快照保留旧口径版本；新旧口径不可直接比较时明确提示，不编造可比差值。分享公开字段白名单继续排除成本、费用及私密财务信息。
- 验收：同一筛选范围、时间点、估值币种和覆盖规则下，各页面数量、成本、估值与收益一致；两种语言和窄屏可完成录入、查看及纠错。

### 内部工作 6：统一回归与完整财务版本发布

- 完成业务规则、数据库事务、备份恢复、HTTP 与 UI 回归；演练中断、失败回滚、重复提交以及当前基线数据保留。
- 使用真实形状的匿名测试数据核对旧记录和新账本，解决歧义记录后再启用完整收益。
- 验证安装/便携运行、版本元数据和产物校验；发布说明列明新财务口径及数据兼容范围。
- 端到端验收必须覆盖“设置录入汇率 → 多币种交易/费用 → 部分出售 → 首页、详情和组合核对 → 备份恢复”，以及修改/缺失汇率、历史快照稳定、中英文和窄屏设置操作。
- 验收：关键用例通过，未实现功能不暴露为正式能力；保留回退副本。财务改造单独发布，不同时混入大型视觉改版或批量导入。

### 财务稳定后的顺序

1. 完成其余页面的国际化重构和固定环境视觉比较；新开发功能从开始就遵守这些要求。
2. 实施数据库分页、统计查询分离及大收藏量基准测试。
3. 优化录入和表格视图，再实现批量修改、CSV/XLSX 导入导出及误操作恢复。
4. 调整分享视觉和可读性，再推进提醒；在线服务继续作为有资源前提的远期方向。

不预设版本号或工期；明确业务和数据边界后再根据实际改动量估算，不改变统一完成、统一验收的交付承诺。业务算法的权威规则仍维护在[财务模型](./financial-history-model.md)，这里仅记录实施依赖和验收顺序。

## 已完成：录入工作台 2.0

### 目标

优先改善最常用的录入和维护流程，让同套卡、同一主体、拆盒或批量图片场景能够连续处理，并减少重复劳动和误录。

### 核心范围

- 连续录入模式：保存后可继续录入、查看详情或复制新增。
- 批量图片导入，建立待处理队列。
- AI 批量识别，但每张卡必须由用户确认后才能写入正式数据。
- 复制上一张卡片的年份、品牌、产品线、Team 等公共字段。
- 常用录入模板，例如同一套卡、同一主体或同一次拆盒。
- 根据卡片主体、年份、产品线、卡号、平行版本和编号提示疑似重复卡。
- 录入草稿箱和中断恢复。
- 图片自动旋转、压缩、正反面排序和失败重试。
- 键盘快捷操作、必填项定位和更清晰的保存反馈。
- AI 识别结果显示置信度和待确认字段。

### 交付状态

已于 2026-08-21 完成。实际交付覆盖 SQLite 草稿与恢复、连续录入、批量图片 WebP 预处理队列、失败重试、公共字段模板、疑似重复提示、键盘工作流，以及需逐卡确认的持久化 AI 候选。复制新增和模板只复用公共字段；编号、证书、图片和财务数据不会被隐式复制。

### 暂不包含

- 不在本阶段引入部分出售和复杂收益计算。
- 不让 AI 在用户确认前直接批量写入正式收藏。
- 不引入服务器账户或云端队列。

### 完成标准

- 连续录入和草稿恢复均有自动化测试。
- 批量任务中单张失败不会丢失其他任务。
- 重复提示只提供判断依据，不自动覆盖已有卡片。
- 旧版单卡录入流程和现有数据保持兼容。

## 已完成：持仓与收益模型

### 目标

让交易历史能够准确表达分批买入、持仓数量、部分出售、剩余成本以及已实现和未实现收益。

### 核心范围

- 分离卡片档案、持仓数量与交易事实。
- 支持同一资产分批买入和部分出售。
- 费用明确关联买入、评级或出售过程。
- 自动计算当前数量、剩余成本、已实现收益、未实现收益和总回报。
- 初期只支持一种明确的成本分配方式，优先考虑移动平均法。
- CNY/USD 分币种计算。
- 继续保持 CNY/USD 独立展示，不在本阶段引入汇率换算。

### 风险边界

- 数据升级与界面重构分阶段完成；界面只读取统一持仓计算结果，不复制财务算法。
- 迁移前必须生成数据库快照，迁移失败不得替换当前数据。
- 必须覆盖分批买入、部分出售、费用归属回填、跨币种隔离和旧备份恢复测试。

### 明确不包含

- 退款、退货、交易取消和冲销。
- 持有过程费用与自动汇率换算。
- 首页卡片缩略图不显示单卡持有数量；数量在卡片详情和财务历史中维护与展示。

### 交付状态

已于 2026-08-24 完成。交付包含初始数量、分批买入、部分出售、移动平均成本、三类费用归属、出售费用绑定、状态自动联动、现有费用一次性回填、无需重启的旧备份升级恢复，以及财务摘要、成本/估值趋势、成本构成、盈亏构成和清晰的逐笔影响展示。

该阶段在早期路线图中曾暂定为 `v1.2.0`，最终根据实际交付范围合并并以 `v1.1.1` 发布。后续路线图不再预先指定版本号。

## 已完成：组合中心

### 目标

将首页摘要和组合分析扩展为独立的收藏组合页面，为日常整理、估值维护和结构判断提供可靠视图。

### 核心范围

- 总估值、成本、已实现收益和未实现收益趋势。
- 按卡片主体、运动、Team、年份、品牌、评级机构和卡片类型分析。
- 数量集中度与估值集中度。
- 最近 30/90/180 天估值变化。
- 估值来源构成、估值时效和过期提醒。
- 未估值、无图片、缺少交易和资料不完整清单。
- 高价值持仓、高成本持仓和已售卡片复盘。
- 将筛选条件保存为收藏视图，例如核心收藏、待评级、在售或待更新估值。
- 支持两个时间点或两个收藏视图之间比较。
- 保存组合分析快照并比较结构变化。

## 远期方向：可选在线服务

### 启动条件

只有在长期服务器、正式 Cloudflare 项目、身份认证方案和运维能力明确后才启动。

### 候选范围

- 用户账户和设备授权。
- 加密的数据同步。
- 冲突检测、操作版本和历史恢复。
- 媒体对象存储。
- 永久分享链接。
- 发布、更新、撤回和访问权限。
- 在线分享版本记录和可选访问统计。

### 明确限制

- 不直接使用云盘同步正在使用的 SQLite 文件。
- 多设备同步必须建立在记录版本、操作日志或服务端事务之上。
- 在线能力应保持可选，本地收藏管理不能因服务器不可用而停止工作。

## 跨阶段体验标准

每个功能阶段都应尽量满足以下体验要求：

- 长表单和复杂编辑自动保存草稿。
- 危险操作提供二次确认、撤销或安全备份。
- 长时间任务显示阶段、进度、成功结果和失败恢复方法。
- 错误信息同时说明发生了什么以及用户可以怎样处理。
- 空状态提供明确的下一步入口。
- 保存成功后允许继续当前工作流，不强制跳转。
- 重要页面支持合理的键盘操作。
- 校验失败后保留用户已填写内容。
- 批量任务支持局部失败，不因单项错误丢失全部进度。
- 新功能必须纳入备份、恢复、当前数据库基线升级和隐私边界评估。

## 跨阶段工程验收标准

每次正式发布前至少完成：

- 使用锁文件在干净环境安装依赖。
- UTF-8、版本元数据和 TypeScript 检查。
- 与新增功能对应的业务规则测试。
- 卡片与分享关键 HTTP 端到端测试。
- 生产构建和打包后运行时冒烟测试。
- 安装包、便携 ZIP、内部版本和 SHA-256 校验。
- 数据库变更必须从当前基线提供升级快照、失败回滚和当前版本备份恢复测试。
- 生产依赖安全审计。
- 更新 README、对应发布说明和本路线图实施状态。

## 规划维护方式

- 开始一个能力阶段前，将其核心范围拆成可验证的开发批次。
- 新需求优先归入最匹配的既定阶段，避免无边界插入当前开发批次。
- 如需调整顺序，应记录调整原因、依赖条件和数据风险。
- 阶段完成后在本文件中标记实际交付结果，并记录最终采用的发布版本；未完成项重新归档。
- 具体版本号在发版收口时确定。小型修复可以单独发布，也可以并入下一阶段，但高风险数据模型必须保持独立、可验证的升级边界。
